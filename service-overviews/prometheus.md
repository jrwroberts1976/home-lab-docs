# Prometheus — Metrics Collection and Time-Series Monitoring

## Purpose

Prometheus is the homelab metrics collection and time-series storage platform. It scrapes metrics from hosts, containers, network services, security tooling and Kubernetes, stores those measurements over time, and supplies the data used by Grafana dashboards, alert rules and automated reporting.

Prometheus is the central point where individual exporters become a coherent monitoring system.

The operating model is:

```text
hosts / containers / applications / network devices / Kubernetes
                         |
                         v
                 metrics exporters
                         |
                         v
                    Prometheus
                         |
             +-----------+-----------+
             |                       |
             v                       v
          Grafana               reporting / analysis
      dashboards + alerts
```

## Current topology

The homelab currently has more than one Prometheus instance.

- TestServer (`main`) runs a Prometheus instance as part of its monitoring stack.
- `ids-01` also runs Prometheus as part of the live Grafana monitoring stack.

These instances must not be assumed to be interchangeable copies of one another. Their Compose files, bindings, targets and operational roles can differ.

The live Grafana Prometheus datasource on `ids-01` is:

```text
name: Prometheus
uid: PBFA97CFB590B2093
url: http://prometheus:9090
```

For Grafana dashboards and central alert evaluation on `ids-01`, this local Prometheus container is therefore the important datasource.

## Main metrics sources

Prometheus collects from several different exporter types.

### Node Exporter

Node Exporter supplies host-level metrics such as:

- CPU;
- memory and swap;
- filesystem capacity;
- load;
- network interfaces;
- host availability;
- custom textfile metrics generated by homelab scripts.

The textfile collector is particularly important because many homelab-specific controls publish their results this way rather than running a dedicated HTTP exporter.

Examples include:

- ASUS router health;
- Pi-hole policy/blocklist metrics;
- network discovery;
- blocked-MAC monitoring;
- CrowdSec activity;
- Restic health;
- software/version checks.

### cAdvisor

cAdvisor exposes Docker/container resource and runtime telemetry including CPU, memory, filesystem and container-state information.

Container state must be checked at three layers when investigating a scrape failure:

1. the container is running;
2. the container is attached to the expected Docker network or published port;
3. Prometheus can actually scrape the target and reports `up=1`.

A running exporter container alone does not prove the scrape path works.

### Blackbox Exporter

Blackbox Exporter performs active service/network probes used to measure reachability and availability independently of host metrics.

This is useful for distinguishing:

```text
host is up
```

from:

```text
service endpoint is actually reachable
```

### kube-state-metrics

Kubernetes state is exported from `k3s-node-01` through kube-state-metrics.

The documented Homelab Defender path is:

```text
Homelab Defender on k3s-node-01
        |
        v
kube-state-metrics 192.168.2.211:8080
        |
        v
Prometheus on ids-01
        |
        v
Grafana on ids-01
```

### Custom application exporters

Where an application does not expose the required metric directly, the homelab often uses a small collector script to generate Prometheus textfile metrics.

This pattern is intentionally simple:

```text
source/API/log/command
       |
       v
collector script
       |
       v
*.prom textfile
       |
       v
Node Exporter
       |
       v
Prometheus
```

## Scrape health

The core Prometheus health indicator for a target is:

```promql
up
```

A value of `1` means Prometheus successfully scraped the target during the most recent scrape. A value of `0` means the target is configured but the scrape failed.

Example query against the `ids-01` Prometheus API:

```bash
curl -sG 'http://localhost:9090/api/v1/query' \
  --data-urlencode 'query=up' | jq .
```

For an individual target:

```promql
up{job="cadvisor",host="ids-01"}
```

The `/targets` API should be used when the reason for a failure is required because it exposes scrape health and the latest scrape error.

## Prometheus configuration is an operational dependency

Prometheus configuration controls what is monitored and how often it is scraped.

Configuration changes can therefore create monitoring blind spots without changing the monitored service itself.

Typical changes include:

- adding or removing scrape targets;
- changing labels;
- changing scrape intervals;
- changing file-based target definitions;
- adding a new exporter;
- moving a monitored service to a different address;
- removing a retired target.

Before removing a target, confirm it is genuinely obsolete. The legacy ASUS scrape target at `192.168.2.220:9106`, for example, was removed only after it was confirmed unused and the Prometheus configuration passed `promtool` validation.

## TestServer configuration and persistent data

The TestServer Prometheus instance is Docker Compose managed.

A recent Stage 6 baseline recorded the following important bind mounts:

```text
/home/james/docker/data/monitoring/prometheus/prometheus.yml
  -> /etc/prometheus/prometheus.yml

/home/james/docker/data/monitoring/prometheus/linux-hosts.yml
  -> /etc/prometheus/linux-hosts.yml

/home/james/docker/data/monitoring/prometheus/data
  -> /prometheus
```

The first two are configuration files. The final path is the persistent mutable TSDB directory.

These must be treated differently during change validation:

- configuration files can be content-hashed and compared;
- the TSDB directory is mutable state and should be validated by path/type/ownership and recovery policy rather than by a fixed hash.

## Container lifecycle authority

The TestServer monitoring Compose definition is owned through the `docker-env` configuration/repository path rather than by ad-hoc `docker run` commands.

The Prometheus image is parameterised through:

```text
PROMETHEUS_IMAGE
```

so a reviewed immutable candidate can be injected into the controlled container-update workflow without editing unrelated service configuration.

A 28 August 2026 Stage 6 engineering baseline captured Prometheus `3.13.1` with a `3.13.2` patch candidate. That document is update-workflow evidence, not the permanent version authority for this Service Overview. Always verify the current running image before an operational change.

## Availability expectations

Prometheus is an observability dependency rather than a direct dependency for most application traffic. A Prometheus outage normally does not stop DNS, reverse proxying or hosted applications from serving users.

However, an outage can cause:

- Grafana dashboards to lose current metrics;
- alert evaluation to enter No Data/Error states;
- security/operations reports to lose evidence;
- host-down events to go unnoticed;
- historical time series to develop gaps.

For this reason, the monitoring platform should be treated as operationally important even where it is not application-critical.

## Monitoring Prometheus itself

Prometheus monitoring should include:

- container/service running state;
- readiness endpoint;
- scrape-target health;
- TSDB/storage capacity;
- query/API reachability;
- configuration reload/validation errors;
- stale custom textfile metrics;
- abnormal scrape duration or target count changes;
- unexpected disappearance of important jobs.

On TestServer the documented readiness endpoint is:

```text
http://127.0.0.1:9090/-/ready
```

A successful readiness response proves the Prometheus process is ready to serve requests, but it does not prove that every configured scrape target is healthy.

## Configuration validation

Where `promtool` is available, validate configuration before reload or restart:

```bash
promtool check config /path/to/prometheus.yml
```

Then confirm the live target state after the change.

A safe change sequence is:

```text
edit authoritative source
        |
        v
review Git diff
        |
        v
validate configuration
        |
        v
apply/reload/recreate
        |
        v
check readiness
        |
        v
check target health
        |
        v
check Grafana / alert impact
```

## Labels and identity

Prometheus labels form the interface used by dashboards and alerts.

Common labels include:

```text
job
instance
host
service
container
```

A target can be reachable but still appear missing from a dashboard if a relabel or target-definition change alters the labels the dashboard expects.

Changes to established labels should therefore be treated as monitoring-interface changes rather than simple cosmetic edits.

## Security controls

Prometheus should be treated as infrastructure-only unless there is a deliberate reason to expose it.

Controls should include:

- restrict network access to the Prometheus API and UI;
- avoid placing credentials directly in scrape configuration where a safer mechanism exists;
- protect configuration files that reference authenticated targets;
- avoid exposing sensitive data as metric labels;
- keep exporter permissions read-only wherever possible;
- do not give monitoring containers unnecessary Docker socket/device privileges;
- validate target additions so monitoring does not become an unintended network-access path.

Metrics are operational data and can reveal hostnames, addresses, software versions and system behaviour even when they contain no passwords.

## Backup and recovery

Prometheus has two different recovery concerns.

### Configuration

Configuration and target definitions should be recoverable from Git or protected configuration backups.

This includes:

- `prometheus.yml`;
- file-based target definitions such as `linux-hosts.yml`;
- Compose definitions;
- custom exporter scripts and systemd units;
- alert/query documentation that depends on specific labels.

### Time-series data

The TSDB contains historical monitoring data.

Whether it must be restored after a total failure depends on the recovery objective. Recent operational history can be valuable for incident analysis and trend comparison, but the monitoring platform should be capable of rebuilding and resuming collection even if historical TSDB recovery is not possible.

Do not treat copying a live TSDB directory casually as a supported backup mechanism. Backup/restore methods should be tested against Prometheus' storage expectations.

## Recovery validation

After restoring or rebuilding Prometheus, verify:

- the configuration validates;
- the service/container is ready;
- expected scrape targets are present;
- critical targets report `up=1`;
- custom textfile collectors are visible;
- Grafana datasource queries succeed;
- alert rules no longer report unexpected No Data/Error states;
- important dashboards show current timestamps;
- expected labels match existing queries.

## Common failure modes

### Exporter is down

Prometheus reports:

```text
up=0
```

Check the exporter service/container first, then its listener and network path.

### Exporter is running but unreachable

Check:

- Docker network attachment;
- published ports;
- host firewall;
- bind address;
- DNS/hostname resolution;
- target address in Prometheus.

### Target disappeared after configuration change

Check:

- file-based service discovery file exists;
- YAML syntax;
- relabel rules;
- target labels;
- config reload status.

### Dashboard shows no data while target is healthy

Check the exact PromQL used by the panel and compare expected labels to the current series.

### Textfile metric becomes stale

The Node Exporter target can remain `up=1` while an individual collector has stopped refreshing its `.prom` file.

Collectors that matter operationally should expose their own timestamp/success metric so staleness can be alerted independently.

## Change rules

1. Treat each Prometheus instance as host-specific unless configuration has deliberately been standardised.
2. Validate configuration before applying it.
3. Use authoritative Git/Compose sources rather than manual container recreation commands as the configuration source of truth.
4. Check both readiness and scrape-target health after change.
5. Preserve labels used by dashboards and alerts unless a controlled migration is planned.
6. Remove targets only after confirming they are obsolete.
7. Monitor custom collector freshness, not just Node Exporter availability.
8. Keep Prometheus infrastructure-only unless exposure is explicitly required and protected.
9. Back up configuration separately from mutable TSDB state.
10. Prove the monitoring path end-to-end from exporter to Grafana after major changes.
