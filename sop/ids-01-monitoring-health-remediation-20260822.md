# ids-01 Monitoring Health Remediation — 22 August 2026

## Purpose

This record documents the engineering checks and remediation completed on `ids-01` while reviewing the **Homelab Engineering Security Runbook - 22 August 2026** and the accuracy of the daily security/recovery reporting.

The review established that several conditions needed to be distinguished from an actual security incident: a transient CrowdSec Local API refusal, a Pi-hole blocklist metrics collector path error, and a non-applicable OpenIPMI service failure.

## Final status

**Status: COMPLETE**

At the end of the work:

- CrowdSec Local API and firewall-bouncer communication were verified healthy.
- Pi-hole blocklist metrics were restored end-to-end through node-exporter and Prometheus.
- `openipmi.service` was identified as non-applicable to this host and masked.
- `systemctl --failed` on `ids-01` returned **0 failed units**.

## 1. CrowdSec enforcement API investigation

### Runbook finding

The 22 August engineering runbook contained a P2 item for a temporary refusal against the CrowdSec Local API on `127.0.0.1:8080`.

### Verification

The host was checked for:

- CrowdSec service state;
- TCP/8080 listener state;
- `cscli lapi status`;
- CrowdSec metrics;
- active decisions;
- recent API/decision errors;
- failed systemd units.

The Local API was available and the firewall bouncer was successfully consuming the decision stream. Recent decision-stream requests were returning successfully.

### Decision

**CLOSED — transient/recovered condition.**

There was no evidence of an ongoing CrowdSec Local API or enforcement failure at the time of verification.

## 2. Pi-hole blocklist metrics collector failure

### Symptom

`pihole-blocklist-metrics.service` appeared in `systemctl --failed` on `ids-01`.

The service is a oneshot collector invoked by `pihole-blocklist-metrics.timer` and runs:

```text
/usr/local/bin/pihole-blocklist-metrics.sh
```

### Root cause

The collector was hard-coded to write its Prometheus textfile output to:

```text
/var/lib/prometheus/node-exporter/pihole_blocklists.prom
```

However, the node-exporter instance on `ids-01` is configured to consume textfile metrics from:

```text
/var/lib/node_exporter/textfile_collector
```

This was the same class of monitoring-path error previously found in the Nebula Sync collector: the collector could produce a metrics file while node-exporter was reading a different directory.

### Remediation

A backup was created:

```text
/usr/local/bin/pihole-blocklist-metrics.sh.bak-20260822
```

The collector output was changed to:

```text
/var/lib/node_exporter/textfile_collector/pihole_blocklists.prom
```

The collector was then run manually and returned exit status `0`.

The systemd service was also started manually and completed with:

```text
status=0/SUCCESS
```

Because this is a oneshot service, returning to `inactive (dead)` after a successful run is expected behaviour.

### End-to-end verification

Node-exporter exposed the following healthy state:

```text
pihole_block_test{category="adult",host="ids-01"} 1
pihole_block_test{category="bypass",host="ids-01"} 1
pihole_block_test{category="gambling",host="ids-01"} 1
pihole_block_test{category="general",host="ids-01"} 1
pihole_block_test{category="threat",host="ids-01"} 1
pihole_block_tests_expected{host="ids-01"} 5
pihole_block_tests_passed{host="ids-01"} 5
pihole_blocklist_health{host="ids-01"} 1
pihole_blocklists_enabled{host="ids-01"} 5
pihole_blocklists_failed{host="ids-01"} 0
pihole_blocklists_hard_failed{host="ids-01"} 0
pihole_blocklists_total{host="ids-01"} 5
```

Prometheus also returned:

```text
pihole_blocklist_health{host="ids-01"} = 1
```

The obsolete file was removed from:

```text
/var/lib/prometheus/node-exporter/pihole_blocklists.prom
```

### Decision

**CLOSED — wrong node-exporter textfile path corrected.**

The blocklist monitoring chain is now verified as:

```text
Pi-hole blocklist collector
  -> /var/lib/node_exporter/textfile_collector/pihole_blocklists.prom
  -> node-exporter
  -> Prometheus
  -> Grafana
```

## 3. OpenIPMI failed service

### Symptom

After the Pi-hole collector failure was cleared, `systemctl --failed` contained only:

```text
openipmi.service
```

### Investigation

The unit was generated by `systemd-sysv-generator` from:

```text
/etc/init.d/openipmi
```

The host had:

- no `/dev/ipmi*` device;
- generic `ipmi_devintf` and `ipmi_msghandler` modules loaded;
- no evidence of a usable local BMC/IPMI interface.

The failed service therefore did not represent an operational management interface used by this host.

### Remediation

The service was disabled and masked:

```bash
sudo systemctl disable openipmi.service
sudo systemctl mask openipmi.service
```

Final state:

```text
Loaded: masked
Active: inactive (dead)
```

### Decision

**CLOSED — non-applicable service disabled/masked.**

The package was not purged, allowing the decision to be reversed later if IPMI support is ever required.

## 5. Reporting lessons

The investigation highlighted weaknesses in the current daily brief/runbook generation logic.

Future reporting should not infer that a control is healthy merely because a timer, service or container exists. Where possible it should validate the complete monitoring/control path and metric freshness.

The daily reporting logic should distinguish at least:

- **PASS / healthy** — positively verified with current evidence;
- **FAIL / degraded** — a control is known to be failing;
- **UNKNOWN / no data** — the health of the control cannot currently be established;
- **NOT APPLICABLE** — the service/control is intentionally unused on that host.

`UNKNOWN` must not be treated as healthy.

The management brief should separately assess security, DNS/policy enforcement, backup/recovery, infrastructure availability and monitoring integrity rather than equating "no compromise" with "no operational issue".
